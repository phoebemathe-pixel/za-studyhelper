The security environment


In very simple terms, security deals with protecting assets from threats that attackers wish to exploit. Section 8.1 in the security PDF deals with some of the aspects you need to be aware of. In particular, you need to be aware of the meaning of at least the following terms:

Asset;
Threat;
Control; and
Attack.
Threats tend to target one (or more) of three information aspects: confidentiality, integrity, and availability. This is known as the CIA triad, and it is discussed in section 8.2 in the security PDF and section 9.1.1 in the textbook. Make sure that you understand the basic idea behind this triad.

Attackers can range from individuals that accidentally exploit threats (and are therefore unintentional attackers), to external entities that want to obtain the information security assets being protected. These assets could be processing resources (which are needed for botnets), or sensitive personal information such as the information obtained during the Experian attack. A significant amount of information in the world is useable or valuable to someone (hence the popularity of ransomware attacks), so security is a constant consideration for any system.


Security mistakes and common attacks


In section 8.1 in the security PDF a number of attacks are mentioned, such as malware and phishing. When dealing with security from an OS perspective, a significant number of threats are caused by common mistakes, a lack of awareness, negligence, and unsafe practices. A few of these are:

Unsecured physical access: While perhaps not as problematic on a home computer, a mobile device such as a smartphone or laptop is always at a high risk of being stolen physically. Smartphones tend to have a lot of sensitive information on them, and can often be used to access bank-, email, and social media accounts. One type of attack, known as a sinkhole attack, can be executed with access to simply one social media or email account. A sinkhole attack exploits the implied trust that exists between various personal accounts and uses that trust to gain access to an increasing amount of personal information. To show how such an attack would work, consider someone gaining access to your email account. This account is used to verify access credentials for other platforms, and can normally be used to reset passwords as well. In addition, most email accounts contain messages and traces of accounts that we logged into, making it possible to both identify and gain access to an individual’s personal accounts using a single email account. Similarly, certain social media platforms such as Facebook allow you to log in to other accounts using the Facebook account as a validation entity. Yet despite this, a significant number of people do not secure their physical devices with a password or something similar, and are therefore highly vulnerable to attacks that exploit the fact that trusted devices are still trusted when the device is stolen, or even left unattended.
Using only one type of authentication: There are primarily three categories of authentication that can be used to identify a user or entity. The most ideal setup would require the use of all three; while this is not always possible, it is usually achievable to use at least two kinds. The three types of authentication are (section 9.6 in the textbook):
Knowledge (“something you know”): By using something only an authorised user is supposed to know, you can reduce the number of entities that can access a system. Examples of knowledge authentication are passwords, passphrases, PINs, and security questions.
Possession (“something you have”): Perhaps the oldest for of authentication is to use something, such as an object or device, to verify the identity of an entity seeking access. While this could be something like a key, a certificate could also arguably be included in this category. Examples of possession authentication are keys, physical access tokens, 2PA (2-Phase Authentication) using a bespoke device or a phone, access cards, and RFID tags.
Attribute (“something you are”): The third type of authentication involves identifying an entity using its unique attributes, for instance identifying a person using their face or fingerprints. While this method is very secure in theory, it suffers from the drawback that authentication cannot be reset if something should go wrong. Multiple sources have shown, for instance, that fingerprint readers can be fooled using a variety of techniques, and you cannot change your fingerprint if someone should gain access to it. The primary example of attribute authentication is biometrics such as fingerprint reading and facial recognition.
Mistaking convenience for heightened security: One of the easier ways to improve the security on a system is to add an additional layer of security, such as an additional authentication type. What often happens, however, is that one authentication type is exchanged for another, such as when a pattern or fingerprint is used instead of a password. While these techniques may sometimes seem more secure, it does not negate the fact that one layer of authentication was sacrificed in exchange for another one. Ideally, especially for secure applications and systems, biometrics are added as an additional requirement alongside a password. This increases the amount of effort needed to successfully authenticate, however, which means that a lot of users select the one over the other. Ultimately, actions like replacing a password with a fingerprint scan does not enhance security, it enhances convenience while giving the impression that security has been enhanced.
Unsafe habits and settings: While it’s not uncommon for people to be aware of the dangers of accessing unsafe digital resources, studies have shown that people persist in their unsafe behaviour despite knowing that it might be unsafe. This is also true for operating system use. One possible contributing factor to this is that people may be unaware that their behaviour is unsafe, while other people simply don’t care. Consider the following instances that each describe a particular kind of unsafe behaviour:
Browsing behaviour assumptions: It is often claimed that websites that engage in illegal activity, such as copyright infringement, are riddled with malware and that any files downloaded from such a site are by definition unsafe. While it is true that there is a heightened risk from using such sites, the risk is not that much greater than using other sites, especially if the site that engages in the illegal activity has a large user base. The mistake that is therefore often made is to assume that legal sites are safe because illegal ones are not – this is simply not true. Just as a large illegal site with many visitors can be reasonably safe (as the users are often likely to police the content of those sites) any legal site can also potentially be compromised by a bad actor. All sites that do not have high levels of security should therefore be considered suspect – legal or not.
Not using additional controls: One of the most popular attack vectors are malicious adverts embedded onto websites. Companies that make use of ads to generate an income tend to embed access to an ad service that delivers those ads, which means that a website owner may end up unintentionally spreading malware if one or more of those ads are compromised. It is common for people to not block ads as a general rule, which means that even visiting familiar sites may cause malware infections. This is not to say that the ad-based business model is necessarily bad, but is does require constant monitoring and verification of each ad if a site is to be kept reasonably safe. It is therefore safer to disable ads as a rule, and only enable them for sites you wish to support financially.
Opening emails from unknown senders: While it may seem common sense to some to not trust suspicious emails, it is an unavoidable fact that the primary attack vector for ransomware is still via email. There are at least two reasons for this: one, a large number of people are still unfamiliar with the maxim that “if it sounds too good to be true, it is”. The second is FOMO (Fear of Missing Out); a significant number of attack emails are structured in such a way that the recipient is made curious about the contents of the email and its attachments. One example is to structure the email in a “here’s you invoice” type of way, which makes the recipient curious about the contents of the attached “invoice”. All emails from unknown sources should therefore be treated with the utmost suspicion.
Hiding file name extensions: It is common practice, especially on Windows (where it is enabled by default) to hide the extensions of known file types. This comes with a risk, however: executable files (i.e. the ones that are most likely to contain malware) can be assigned any icon – even one that corresponds to the icon of a known file type. To show the impact this can have, consider the following example: a user downloads an executable file that appears to be a PDF. The reason it appears to be an executable is that the file has the Adobe icon and the file name does not show that it is an executable. The user opens the file, which launches the malware. This particular piece of malware, in order to hide its true purpose, creates a copy of itself in a system folder somewhere, and launches the copy. The copy, noticing that it is in the system folder, overwrites the original executable file with an actual PDF file of which it had the binary data available, and opens the PDF file. The user, thinking that the PDF file is just taking a bit longer to open, is unaware that his machine has been infected and will not be able to easily trace the attack back to the original attack file, as it has been replaced by a real PDF file. By hiding file name extensions, these types of attacks become much easier for an attacker to launch successfully.
Outdated systems: Possibly as a result of Microsoft’s infamously bad history with system updates, it is very common for active installations of Windows to be outdated. While a large number of the exploits that are routinely fixed do not necessarily pose a risk to the average user, it is still good practice to keep the security systems of any OS as up to date as possible. This should also be the goal with other device such as smartphones, but updates to smartphone operating systems often require that network service providers validate the updates first to ensure that the updates won’t cause damage to devices – a process that can take weeks or even months. It is therefore likely that a smartphone’s OS will be outdated most of the time, and the appropriate care should be taken at all times.
OS snobbery: It used to be held (and still tends to) that Linux and Apple’s operating systems are safer than Windows because they are less susceptible to malware (or “immune” in Apple’s case). This belief may have a direct impact on the behaviour of the operating system’s users, as the belief that an OS doesn’t get viruses may encourage or enable unsafe behaviour. While it is true that Linux has a significantly smaller number of viruses than Windows does, it is caused by the fact that Linux has a much smaller user base (at most 2% of PCs, by some estimates, run Linux), most of whom tend to be hobbyists who often have at least some understanding of security. The chances of a successful infection on a Linux system is therefore generally much smaller than on Windows. This means that there is more value in developing malware for Windows than Linux, as the potential “return-on-investment” is greater due to the larger number of users. This is not true for Apple’s operating systems, however: in recent years, the amount of malware affecting Apple’s operating systems has grown substantially, and Apple devices are now more vulnerable than Windows devices, despite the fact that there are fewer Apple devices than devices running Windows. This observation is supported by the fact that Apple devices recently showed a greater infection rate than Windows devices. It should therefore never be assumed than an OS is safe “just because it is”, or because it “always used to be”.

Basic OS specific attack types

The following are some of the kinds of attacks you can get that mostly affect operating systems. Some of these attacks are prevented in software by throwing exceptions when the associated condition is encountered (provided a sufficiently advanced programming language is used). As such, you may notice that some of these attacks have names similar to exceptions you may have encountered in the past. The attack types are:

Buffer overflow attacks: An array, from the perspective of memory, is a reserved space with a fixed size. Buffer overflow occurs when there isn’t bounds checking to make sure that the array is large enough to contain the data that is being stored in it. The consequence of buffer overflow is that the data being written to one array overwrites the data stored in the adjacent memory space of another process. When used as an attack, the data that is written to the other process’s memory space may contain specially tailored data or instructions aimed at hijacking that process’s control flow and functions. Buffer overflows are used because the base language of operating systems, C, is not known for enforcing hard array bounds. Furthermore, the attacking process will be regarded as being “safe”, because it has its own memory space and IPC is strictly controlled. By exploiting the fact that there are no bounds checking on arrays, which makes buffer overflows possible, the process can ignore these restrictions. There are a number of ways in which this technique, where the data and execution code of another process is modified in memory, can be used (see section 9.7.1 in the textbook for a description of these attacks). In order to protect against buffer overflow type attacks, the following techniques can be used:
Stack canaries, to protect the execution stack;
Data Execution Prevention, to prevent code stored in the data area of a process’s memory from being executed as code; and
Address Space Layout Randomisation, to prevent attacking processes from reliably constructing code using code already available in the victim process’s code area.
Format string attacks: C uses two distinct types of strings: regular strings, which contain plain text, and format strings which contain addition information about how the string should be processed. While most of these instructions deal with how the string should be displayed on-screen, some of them are more complex, such as “store the string to memory”. By using these instructions, and manipulating how they are processed in application code, an attacker can potentially inject attack code into the code of another application using format strings.
Dangling pointers: C makes use of pointer to indicate where in memory an application’s data structures should store data, but also allows for user applications to indicate when they are done with the memory space a particular pointer is pointing to. A dangling pointer is a pointer that points to memory that has already been freed and may already have been used by another process (remember that processes take turns to run). The pointer, however, is still valid and can potentially be used to modify the memory data of another process.
Null pointer dereference attacks: When null pointer dereference (loading values stored at a location in memory) attacks are used, an attacker may inject code into the kernel’s memory area that corresponds to some function that has not been initialised yet (and is therefore NULL). Then, by dereferencing the NULL pointer, the attacker causes the kernel to run the injected code with kernel access.
Integer overflow attacks: Computers are limited in the sizes of numbers that can be stored in memory. Integers, in particular, are usually stored using 8, 16, 32, and 64-bit memory spaces. When an arithmetic operation is done on two especially large integer values, it is possible that the value is too large to store using the valid data structures. A common outcome of this that the result of the operation results in a negative value. One way in which this can be used it to trick the OS into creating a memory space that is much too small for the data being loaded, thus creating the opportunity for a buffer overflow attack.
Command injection attacks: Command injection attacks (which also include SQL injection attacks) involve modifying the commands another application executes ever so slightly so that the application is not aware that it is executing attack commands. As shown, modifying the commands of other processes can be accomplished in any number of ways, so injecting attack commands into existing functions is possible. With SQL injection attacks, it is possible to inject unwanted SQL commands into legitimate SQL queries before they are sent to the DBMS.
Time of Check to Time of Use attacks: The final type of attack deals with race conditions that may be caused if an application checks to see if it has permission to execute a particular task some time before (or sometime after) actually doing the task. If enough time elapses between the permission being granted and the task being executed, it is possible for an attacking application to jump in and exploit that time lapse. As an example, consider an application requesting user credentials before giving access to a file. In this example, the application gets the credentials (username and password) when starting up, before checking the file system to find the required file. If the attacking process gets its turn from the scheduler before the application can use the credentials, it can, for instance, replace the file with its own in order to capture the user credentials.  
Logic bomb: A logic bomb is a type of attack that causes significant damage to systems at some time in the future. This attack could potentially be used by programmers fearing for their job (in which case it may be used akin to ransomware), or it can be used to cause malicious damage following a viral infection.
Back doors: A back door is an intentional vulnerability built into a security system by the programmer(s), such as hardcoded passwords. Back doors are intended to provide guaranteed access to a system, and their intentional inclusion by a development company (e.g. for commercial software) is often considered unacceptable.
Spoofing and phishing: (see 8.1 in the security PDF) Spoofing and phishing are two similar (and often confused) attacks that function by mimicking legitimate actors and systems. The primary difference between these two attacks is their distinct end goals: phishing is focussed on obtaining information (often using social engineering), whereas spoofing is used to deliver an attack.
Malware: Malware comes in a variety of forms, some of which are discussed in section 9.9 of the textbook. Some of these kinds of malware are:
Trojans: Named after the wooden horse the Greeks used to gain access to the city of Troy in the Odyssey, trojans are any kind of virus that is hidden in software and that is then executed voluntarily, albeit unknowingly, by a user.
Virus: A virus, simply stated, is a small program that attempts to create duplicates of itself when it is run. Viruses, apart from replicating, are also used by attackers to damage systems and obtain sensitive information. Not all viruses are equally dangerous, as some will just try to replicate themselves to take away system resources (rabbit), while others will infect system files in order to allow the attacker to take the system over completely.
Worms: Unlike a virus, which needs to be executed by a user before it can replicate, a worm is self-replicating, i.e. it installs itself on vulnerable systems and replicates itself without user interaction being necessary.
Spyware: Spyware is software that is installed on a system, without the owner of the system being aware of it, that monitors the state, actions, and data on the system and reports that information to a third party. While not all monitoring software is necessarily spyware, any software that intentionally violates the privacy of the user and does so without the user’s knowledge can (and perhaps should) be considered spyware.
Rootkits: A rootkit is a type of software that allows an attacker to gain control over a system without being detected. 5 types of rootkit are discussed in section 9.9.5:
Firmware rootkit is a rootkit that flashes itself onto the BIOS/UEFI of a machine.
Hypervisor rootkits move the entire operating system to a virtual machine that it controls. Because the rootkit is not situated in the operating system or the files it has access to, it is very difficult to detect it.
Kernel rootkits infect the operating system with a rootkit driver that runs in kernel mode. These rootkits can replace functioning drivers with infected drivers that contain both the original drivers and the rootkit.
Library rootkits infect system libraries on order to gain control using infected system calls. Library rootkits also gain access to all of the information passed to the infected library using such system calls.
Application rootkits are hidden inside large applications and try to stay hidden by not taking actions that differ greatly from what the application normally does (create files, access certain system folders, access the Internet, etc.)
Ransomware: Due to the age of the textbook, this type of malware is not mentioned. However, because of how common this type of malware has become, it deserves mention. The basic functioning of ransomware is as follows: an attacker, usually using email, sends an attack to a victim. This attack is commonly an Excel file with an embedded macro. As macros are disabled by default, the Excel file is structured in such a way that the victim is fooled into thinking that macros need to be enabled. Once macros have been enabled, the macro in the attack Excel file downloads a file, sets its file attributes so that it can be started without the user noticing, and then starts the application. This application then generates encryption keys, uploads the decryption keys (which may be different from the encryption keys if asymmetric encryption is used) to a server on the Internet, and begins to encrypt selected files on the victim machine. Once a large enough number of files have been encrypted, a ransom message is displayed to the user to inform them that their files have been encrypted and that they have a limited amount of time to pay the ransom before the decryption keys are destroyed. The ransom messages also often include step-by-step instructions on how to pay using some form of digital currency, such as Bitcoin. While the Excel macro method is discussed here, as it is common and fairly easy to use, there are other methods that can be used to deliver the malware to the target machine. These techniques, such as infected ads, viruses, worms, spoofing, and rootkits, have already been discussed.
